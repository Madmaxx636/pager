# Pager 1.0 checklist

Where things stand and what has to happen before a 1.0. Last checked 2026-11-04, at version 0.6.14. Each line says how it was checked, so it can be checked again.
**Blocker** = do not call it 1.0 without it. **Should** = expected for 1.0, can slip with a written reason. **After** = deliberately later.

## Blockers

| # | What | State | Notes |
|---|---|---|---|
| B1 | **Android release signing key** | Open | Every published APK is signed with the standard Android *debug* key (SHA-256 `09:BF:62:A3:48:AF:DA:14:...`, found with `apksigner verify --print-certs`). A real release key exists (`~/.config/pager/android-release.keystore`, `23:F7:19:7A:...`) but is unused, because phones carry the debug key and Android refuses an update signed with a different one. Anyone can build an app signed with the debug key, so it proves nothing. Plan: rotate with a signing lineage (`apksigner rotate`, APK Signature Scheme v3): Android 9 and up update in place; Android 8 phones reinstall once. Test on a spare phone first. SECURITY.md was wrong about this and now says so. |
| B2 | **Phone keys and sign-in token are stored in the clear** | Open | The crypto store (`filesDir/e2ee`, opened with no passphrase) and the token (SharedPreferences) rely on Android's file encryption and app sandbox. Needs a store passphrase kept by the Android Keystore and a migration that cannot lose keys (the thing we are trying to stop happening). Web keeps keys in IndexedDB and the token in localStorage (a browser cannot do better); the desktop app can use the OS keychain (Electron `safeStorage`). Prove the migration in a test before shipping. |
| B3 | **The cause of "waiting for the keys" is not confirmed** | Open | Fixed on the way: the first-run key screen hid the key (0.6.12), sign-out deleted keys without warning (0.6.11), keys were wiped on a server-ended sign-in (0.6.11), duplicate key uploads (0.6.10). The server shows no fault. Needs a real run on the phones with 0.6.14 and its Encryption details log if it happens again. Close only when two weeks of normal use shows no case. |
| B4 | **Backups and keys have one copy** | Open | Nightly encrypted backups exist and restore was tested, but they sit on the server. The backup private key, the update-signing key, the Android release keystore and the vault key each exist in one place. Copy them off the machine (and a backup off the server) and write down where. Losing the update-signing key means no app can ever be updated again. |
| B5 | **Real-device testing of the phone app** | Open | The e2e suite drives the web and desktop code in a browser. The phone app has unit tests and lint only, no emulator, so first-run key screen, restore, sign-out, calls and the background service have not been exercised by a machine. Add emulator smoke tests (CI runners support them) or a written manual test pass. |
| B6 | **Upgrade path** | Open | Nobody has tested going from an old version (0.5.x) to the 1.0 build with real data on phone, desktop and server. |
| B7 | **Independent security review** | Open | SECURITY.md says there has been none. Not needed for a family server; needed before offering it to a company. |

## Should

| # | What | State | Notes |
|---|---|---|---|
| S1 | Device verification / cross-signing | Open | A new device is trusted through the recovery key only (SECURITY.md). Companies will ask for it. |
| S2 | Windows checks on a real Windows PC | Open | Taskbar unread number, "launch at login" switch, uninstall removing the login entry, the installer, update flow, SmartScreen warning (the installers are unsigned; a code-signing certificate would remove it). All written from the docs, none seen working. |
| S3 | Android lint baseline | Open | 71 findings (15 errors) are hidden in `android/app/lint-baseline.xml`. Read them once and either fix or write why each stays. |
| S4 | Android 15 | Open | Target is 34. Targeting 35 limits how long the always-on sync service (type `dataSync`) may run; needs a plan before the target is raised. |
| S5 | Run the e2e workflow on GitHub once | Open | `.github/workflows/e2e.yml` is written but never run there. Also decide whether it runs on every push. |
| S6 | Accessibility pass | Open | Phone icon buttons are announced as buttons (0.6.10); nothing else audited. Check screen-reader order and focus on web and phone; touch targets are 40 dp (48 is the guideline). |
| S7 | Dependency review | Open | `npm audit`: web 0 issues; desktop has 17 in build tools only (not shipped). Pin and review before release; produce a software bill of materials. THIRD_PARTY_LICENSES.md to be regenerated from the final lock files. |
| S8 | Windows/Linux packages | Open | AppImage and .deb exist. No signed apt repository; the .deb update asks for a password (pkexec). |
| S9 | Native Qt app | Decision | Frozen at 0.5.15 without the recent features. Either bring it up to date, label it experimental, or leave it out of 1.0. |
| S10 | Bridges not covered by tests | Open | The e2e server has no bridges. Login flows and message paths for each bridge are only tested by use. A smoke test per bridge against its real service is not possible in CI; write a manual checklist. |
| S11 | Documentation | Open | DEPLOY.md and README are current. Still missing: a short threat model, an admin guide (backups, upgrades, what the nightly maintenance does, what to do when a bridge breaks), and a plain-words "what can the server see" page. |
| S12 | Log upload (optional) | Open | Apps keep problems on the device (0.5.x to 0.6.5). An opt-in "send this log to my server" button was designed, not built. |

## Done and checked

- **Server:** bridges and Synapse (1.164.2) pinned to exact versions; nightly maintenance (restart stopped services, backup, bridge and Synapse patch upgrades with rollback, cleanup); log watcher with Admin > Logs; nightly backups locked with a public key, `pager verify` and `pager restore` tested; manual backups also locked.
- **Encryption flows (web and desktop, in e2e):** a new account is shown its recovery key and cannot skip past it unsaved; a message is read live and its key backed up; a second device shows it locked and says why; a wrong key is refused; the right key unlocks it; signing out and back in as a new device and entering the key brings history back; a reminder bar while keys are not backed up; sign-out warns first.
- **Screens:** every main screen at 360 x 500, 480 x 720, 800 x 600, 1180 x 760 and 1920 x 1080, in the browser and as the Linux desktop shell: nothing sticks out of the window; a normal session records no problems in Logs.
- **Apps:** signed update information on desktop; checksum and same-key check on Android; call button for WhatsApp, Signal, Messenger and the dialler; plain HTTP refused except on the local network; media cache capped and swept.
- **Tests that run:** web 221, API 46, desktop shell 14, log watcher 20, Android unit tests (33 files), end-to-end 25 (`e2e/`), lint on every push, shell scripts parse.

## After 1.0

- Calls between Pager users (WebRTC / Element Call with a TURN relay and LiveKit). Bridges cannot carry calls.
- A Pager-only mode for companies: single sign-on, retention and audit, admin roles, device management, an on-premises installer.
- Reproducible builds; an app store listing.

## How to check this list is still true

```bash
cd app && npx vitest run && npx tsc --noEmit          # web
cd e2e && npm test                                    # end to end (about 5 minutes)
cd android && ./gradlew :app:lintDebug :app:testDebugUnitTest
apksigner verify --print-certs pager-android-*.apk    # which key signed the phone app (B1)
ssh <server> 'cd pager/server && ./scripts/maintenance.sh --status'   # nightly upkeep
```
